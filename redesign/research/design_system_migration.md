## 1. Migration strategy: token-first vs parallel v2 vs in-place; codemods; staying shippable; what big companies learned

### Takeaway
Every large migration studied fixed the foundation layer first (primitives → semantic/functional → component tokens) so one change propagates everywhere, and shipped the visual switch behind a flag with internal dogfooding and an easy old/new toggle before a staged rollout. Codemods were used only to *suggest* mappings and always required manual review; lint rules then locked in the result. For a single-owner app with an owned component wrapper layer (`app/ui`), the cheapest safe path is token-first + in-place restyle of `app/ui` keeping props APIs, with a temporary token-level "skin" switch for old/new comparison instead of a parallel v2 component tree.

### Cited Findings
**GitHub Primer**
- Primer's colours are layered: "base tokens" (colour scales), "functional tokens" and "component tokens", with higher-level tokens referencing lower ones, so the team could "make color contrast changes in one place" — [GitHub blog: Primer's color system](https://github.blog/engineering/user-experience/unlocking-inclusive-design-how-primers-color-system-is-making-github-com-more-inclusive/)
- Rollout of the new colours used a feature flag: qualitative interviews with colleagues with the flag on, then the flag enabled for all staff and monitored "for a few weeks while collecting feedback"; the team scoped the change to accessibility to "make the smallest possible change to the overall user experience" — [GitHub blog](https://github.blog/engineering/user-experience/unlocking-inclusive-design-how-primers-color-system-is-making-github-com-more-inclusive/)
- Primer Primitives v9.0.0 moved functional tokens onto new light/dark scales and shipped a migration table mapping old base-scale steps to new ones per theme (light, dark, dark high contrast, dark dimmed, light high contrast); consumers using base scales directly had to change how they apply colours — [primer/primitives v9.0.0 release](https://github.com/primer/primitives/releases/tag/v9.0.0)
- Primer CSS v16 replaced Sass colour variables with functional CSS variables that change with the active colour mode, renamed presentational utilities to functional ones (e.g. `text-gray-dark` → `color-text-primary`), used `data-color-mode="auto"` + `data-light-theme`/`data-dark-theme`, and had to update its stylelint config so `var(--color-…)` was accepted — [primer/css PR #1186](https://github.com/primer/css/pull/1186) (via search summary of the PR and v16 migration guide)

**Shopify Polaris (v12, 2023)**

- Shopify ran the new design language as an opt-in beta first ("Beta access to Shopify's new design language" page) — [Polaris: new design language](https://polaris.shopify.com/new-design-language) (title only seen in search; flag mechanics not verified)

**Atlassian**
- Staged workflow: learn tokens → designers apply tokens in Figma → developers set up theming and theme switching → update design-system components (already tokenised) → replace raw values with the codemod → test and review in-app with a Chrome extension that toggles themes and tracks migration progress — [Atlassian: Migrate to tokens](https://atlassian.design/foundations/tokens/migrate-to-tokens)

- Atlassian applies and tests tokens across an entire experience before releasing new colours (e.g. dark mode) publicly — [Atlassian: Migrate to tokens](https://atlassian.design/foundations/tokens/migrate-to-tokens)

**Linear (March 2024 redesign)**
- Only three product designers; explorations from November 2023, core project about six weeks; engineers coded in pairs in the afternoons while designers iterated; first working version by end of week one — [Linear: How we redesigned the Linear UI (part II)](https://linear.app/now/how-we-redesigned-the-linear-ui)

### Inferences
- **Token-first, keep component APIs.** Primer, Polaris and Atlassian all put the new language into the token layer and component library first and only then touched product code. Splitune already routes all colour through `@splitune/ui-tokens` and `app/ui` (enforced by `check-ui-tokens.mjs`), so most of the visual change can land by redefining primitives and semantic roles plus restyling `app/ui` internals, without touching `app/features/*` call sites.
- **Parallel v2 vs in-place.** Parallel v2 components behind a flag (Polaris beta, Linear flag) buy time for many teams/external consumers. Splitune has one owner and one consumer of `app/ui`, so a v2 tree mostly doubles maintenance. Better middle ground: a temporary *skin* switch at the token layer (e.g. `data-skin="night"` vs current, both token sets loaded) so old/new can be toggled in Storybook and dev builds the way Linear used a dev-toolbar toggle; delete the old skin in the cleanup stage. Component restyles land in place, one component family per PR.
- **Shippable between steps.** Each stage must leave `dev` green (lint, typecheck, tests, stories, e2e) and visually coherent under the *default* skin. Until the final flip, the new skin is opt-in, so half-migrated screens are never the default.
- **Codemods.** Splitune's surface is Tailwind classes, not Sass variables, so codemods are mostly class renames when semantic role names change (e.g. `bg-card` → `bg-surface-1`). Keep role names where meaning is unchanged (zero call-site churn); where a rename is needed, use a mechanical rename script + review, as Atlassian/Polaris did, followed by a lint rule banning the old name (Atlassian's `no-deprecated-design-token-usage` pattern, implementable as an extra list in `check-ui-tokens.mjs`).
- **Scope control (Linear).** Freeze the scope per stage: visual language and component internals first; IA/navigation changes in the mockups should be separate, later steps. Put deferrals in an explicit list rather than letting workers decide.
- **Concrete staged playbook (proposed):**
  0. *Baseline.* Record current Playwright screenshots, `toMatchAriaSnapshot` structure snapshots of key screens, and perf traces (§5) so regressions in behaviour/structure are separable from intended visual change.
  1. *Mockup ingestion.* Vendor mockups read-only into the repo (hash-pinned); render them in the pinned Playwright Docker image at the same viewports/themes to produce reference PNGs; extract the shared CSS's token values and component classes into a machine-readable inventory; write a mapping table mockup class → `app/ui` component + variant, with unmapped patterns escalated to the owner, not invented.
  2. *Token layer.* New OKLCH primitives + semantic roles + component tokens, Daylight generated from the same roles; update `CONTRAST_PAIRS`/gamut tests first (tests red → green); new skin opt-in.
  3. *Fonts.* Instrument Sans + JetBrains Mono via `subset.sh`, metric-matched fallbacks, preload budget (§6).
  4. *`app/ui` components*, one family per PR (buttons/inputs → overlays → music-specific kit), stories for every state, story screenshots compared to mockup component crops.
  5. *Screens*, one per PR, in an order that front-loads the practice screen (perf-sensitive) and the most-used flows.
  6. *Flip default skin*, run the full design QA checklist (doc 28 §5) on every screen, then delete the old skin, old roles and dead variants; lint bans deprecated names.
  7. *Hardening*: keyboard-only journeys, reduced motion, perf gates, usability round.

## 2. Token architecture in 2025–2026: OKLCH primitives → semantic roles → component tokens; light/dark from the same roles; Tailwind v4 `@theme`/`@theme inline`; contrast checking in CI

### Takeaway
The current consensus is three tiers (primitive OKLCH scales → semantic roles → component tokens), with each theme being a different mapping of the same role names to primitive steps, generated from a few inputs (Linear: base, accent, contrast). In Tailwind v4, define themes as plain CSS variables on `:root`/`[data-*]` selectors and map them into utilities with `@theme inline` so utilities resolve at the use site; theme variables themselves must be top-level. Contrast must be checked by script over all pairs × all themes on every PR (Primer), which Splitune already does and must extend to the new roles before any component work.

### Cited Findings
- Tailwind v4: "When defining theme variables that reference other variables, use the `inline` option"; without it "your utility classes might resolve to unexpected values because of how variables are resolved in CSS" (a `var()` resolves where the theme variable is defined, not where it is used) — [Tailwind docs: Theme variables](https://tailwindcss.com/docs/theme)
- Tailwind v4: theme variables "are also required to be defined top-level and not nested under other selectors or media queries"; `:root` is recommended for plain CSS variables that shouldn't map to utilities; `@theme static` always emits all variables (default emits only used ones); `--color-*: initial` removes the default palette and `--*: initial` removes the whole default theme; themes can be shared across a monorepo by importing a CSS file — [Tailwind docs: Theme variables](https://tailwindcss.com/docs/theme)
- `oklch()` is Baseline "Widely available" (across browsers since May 2023); relative colour syntax converts any origin colour into OkLCh inside `oklch(from …)` — [MDN: oklch()](https://developer.mozilla.org/docs/Web/CSS/color_value/oklch)
- A web.dev article (Dec 11, 2025) derives a full theme from one `--base-color` with `oklch(from var(--base-color) l c calc(h + 120))` for accents, `color-mix(in oklab, …)` for borders/surfaces, `color-scheme: light dark`, and `light-dark(lightValue, darkValue)` per token, with a `data-scheme` attribute to override — [web.dev: Color themes with Baseline CSS features](https://web.dev/articles/baseline-in-action-color-theme)
- **[conflict]** Browser versions for relative colour syntax and `light-dark()` differ between secondary sources (one gives Chrome 119+/Firefox 128+/Safari 16.4+ for relative colour, Chrome 123+/Firefox 120+/Safari 17.5+ for `light-dark()`); check MDN BCD — [Vivian Voss blog](https://vivianvoss.net/blog/oklch-colour-system)
- Linear generates light and dark themes from three variables (base, accent, contrast) in LCH instead of 98 hand-set variables — [Linear part II](https://linear.app/now/how-we-redesigned-the-linear-ui)
- Evil Martians' Harmony palette uses OKLCH + APCA with "equal contrast within lightness groups" and "mirrored contrast pairs", with P3 options; Harmonizer generates palettes "with consistent chroma and contrast across all levels and hues"; `apcach` composes colours to a target APCA contrast — [Harmony on npm](https://www.npmjs.com/package/@evilmartians/harmony), [Evil Martians: OKLCH ecosystem](https://evilmartians.com/chronicles/exploring-the-oklch-ecosystem-and-its-tools)
- Primer found "over 100 color pairs" needing checks; manual Figma checks were too slow, so a script changes tokens in code and checks contrast for all tokens across all themes (CLI table of pass/fail), blending semi-transparent colours in two steps; it runs in seconds as a GitHub Action on every PR so a contrast-breaking change is caught "before it makes it into production" — [GitHub blog](https://github.blog/engineering/user-experience/unlocking-inclusive-design-how-primers-color-system-is-making-github-com-more-inclusive/)
- Shadcn-style token sets keep the same role names and redefine values under `:root` and `.dark`, typically raising lightness for dark-mode accents — [fortress-shadcn theming docs](https://fortress-shadcn.dashboardpack.com/docs/theming) (third-party template docs; illustrative only)

### Inferences
- **Generate at build time, not at runtime.** Splitune has more than two appearances (Light/Dark/Stage × contrast normal/more × density), and `light-dark()` only switches between two `color-scheme`s, so it can't express Stage or contrast-more on its own. Relative colour syntax at runtime also makes contrast tests harder (values only exist after cascade). Recommended: a small TS generator in `packages/ui-tokens` that takes the Night Rehearsal inputs (graphite hue/chroma, amber hue/chroma, contrast level, à la Linear) and emits static OKLCH primitives per ramp plus per-appearance role maps (`themes.css`), checked into git and covered by `contrast.test.ts`/`palette.test.ts`. Daylight = same roles mapped to mirrored ramp steps (Harmony's "mirrored contrast pairs" idea).
- **Gamut.** The existing tests require every colour to sit inside sRGB. A saturated OKLCH amber can fall outside sRGB; either keep the amber ramp in-gamut (clamp chroma in the generator) or add a deliberate `@media (color-gamut: p3)` tier with sRGB fallbacks and adjust the gamut test explicitly — do not let workers loosen the test.
- **Tailwind mapping.** Keep the cleared namespaces; map each semantic role via `@theme inline { --color-surface: var(--surface); … }` and define `--surface` per appearance under `[data-appearance=…]` selectors (top-level rules, outside `@theme`). The snippet seen in `theme.tailwind.css` uses `@theme { … }` for namespace resets; whether colour mappings already use `inline` should be checked before changing anything (behaviour differs when roles are redefined deeper in the tree, e.g. Stage on a subtree).
- **Contrast in CI.** WCAG 2.2 still uses the WCAG 2.x relative-luminance ratio (4.5:1 normal text, 3:1 large text and non-text UI/focus indicators under 1.4.11); APCA can be reported as advisory but cannot replace the WCAG ratio for an AA claim. Add Night Rehearsal-specific pairs: text on amber (likely needs dark text), amber focus ring vs graphite surfaces and vs amber-filled controls, muted text on every surface elevation, disabled states (exempt from 1.4.3 but should stay legible), selection/loop overlays, and every translucent overlay over every surface it can sit on (Primer's two-step blending; Splitune already does `over()`).

- Exact Baseline status of `light-dark()` and relative colour syntax not confirmed from MDN BCD in this session.

## 3. Translating mockups to code with AI agents: source of truth, fidelity checks, visual regression tools, design QA, stopping one-off components and raw colours

### Takeaway
Practitioner reports agree that agents improve markedly when screenshot capture is mandatory and the comparison target is fixed, but that LLMs are poor at judging spatial similarity from images, so the loop should be driven by measurements (pixel diffs with thresholds, computed styles, bounding boxes, accessibility-tree structure) with an iteration cap. Playwright gives everything needed locally (`toHaveScreenshot`, `toMatchAriaSnapshot`, `getComputedStyle` probes) and is free; hosted tools (Chromatic, Argos) are optional and conflict with personal mode. One-off components and raw colours are best stopped mechanically: cleared Tailwind palette, raw-colour/arbitrary-value lint, import restrictions, and giving agents a machine-readable component inventory (Storybook MCP / components manifest).

### Cited Findings
- `expect(page).toHaveScreenshot()` retakes until two consecutive captures match, compares against a stored baseline and fails beyond tolerance; keeping expected/actual/diff images helps triage; a loose threshold lets real changes through, so tighten only after rendering is deterministic — [techyorker: screenshot tests for AI coding agents](https://techyorker.com/visual-screenshot-tests-playwright-guardrails-for-ai-coding-agents/) (secondary)
- Playwright `toHaveScreenshot` options: `animations` (default `"disabled"`: "finite animations are fast-forwarded to completion… infinite animations are canceled to initial state"), `caret` (default `"hide"`), `clip`, `fullPage`, `mask` (+ `maskColor`, default `#FF00FF`), `maxDiffPixelRatio`, `maxDiffPixels`, `omitBackground`, `scale` (default `"css"`), `stylePath`, `threshold` (default 0.2, YIQ), `timeout` — [Playwright PageAssertions API](https://playwright.dev/docs/api/class-pageassertions)
- Snapshot names include browser and platform (e.g. `example-test-1-chromium-darwin.png`); "For consistent screenshots, run tests in the same environment where the baseline screenshots were generated"; `stylePath` can hide dynamic elements; move the mouse away before capture (`page.mouse.move(-1, -1)`) — [Playwright: Visual comparisons](https://playwright.dev/docs/test-snapshots)
- `toMatchAriaSnapshot` matches the accessibility tree against a YAML template that is "a constraint, not necessarily a complete serialization"; supports partial matching, regex names, `/children: equal|deep-equal` for strictness, `page.ariaSnapshot()`/`locator.ariaSnapshot()` to extract, and separate `*.aria.yml` files shared across browsers — [Playwright: Aria snapshots](https://playwright.dev/docs/aria-snapshots)
- Vitest 4 (Oct 2025) made Browser Mode stable and added `toMatchScreenshot` visual regression (e.g. `await expect(page.getByTestId('hero')).toMatchScreenshot('hero-section')`); providers are separate packages (`@vitest/browser-playwright`); `page` now imports from `vitest/browser` (old `@vitest/browser/context` deprecated) — [InfoQ: Vitest 4 browser mode](https://www.infoq.com/news/2025/12/vitest-4-browser-mode), [Vitest 4 blog](https://main.vitest.dev/blog/vitest-4)
- Practitioner pattern: capture → pixelmatch diff → feed diff into the next edit, repeat — [egghead: AI-driven design workflow with Playwright MCP](https://egghead.io/ai-driven-design-workflow-playwright-mcp-screenshots-visual-diffs-and-cursor-rules~aulxx); the main gain came from making capture non-optional, since multimodal agents can describe what they see — [DEV: screenshot feedback loop](https://dev.to/yureki_lab/how-i-gave-my-ai-coding-agent-eyes-a-screenshot-feedback-loop-for-ui-work-jce)
- Counter-view: the screenshot-eyeballing loop "breaks because you're asking an LLM to do something it's bad at: spatial pixel comparison"; anti-aliasing and font metrics make correct implementations look slightly off; past ~8 iterations without a shrinking diff the agent is likely stuck — [buildmvpfast (search snippet; page returned 403)](https://www.buildmvpfast.com/blog/figma-to-code-pixel-perfect-loop-ai-agent-screenshot-iterate-2026)
- uiMatch compares a Playwright render to a Figma node and reports pixel, layout, style, colour and text differences with a "Design Fidelity Score" and pass/fail (experimental) — [kosaki08/uimatch](https://github.com/kosaki08/uimatch)
- A `ui-from-mockup` agent skill pairs a render-screenshot-compare loop with an extracted spec and PNG diff heatmaps, and states that if an HTML mock and its rendered screenshot disagree, the rendered screenshot wins — [skills.lc: ui-from-mockup](https://skills.lc/psaxde/skills/psaxde-skills-ui-from-mockup-skill-md) (community skill)
- **[outdated]** Lost Pixel: the team announced it is joining Figma and shutting down the visual testing product — [Lost Pixel blog](https://hn.jakechampion.name/reader/https://www.lost-pixel.com/blog/lost-pixel-team-is-joining-figma) (reader mirror); its OSS mode is reported unmaintained — [Argos blog (vendor)](https://argos-ci.com/blog/lost-pixel-alternatives)
- Argos claims MIT licensing for the whole platform and accepts screenshots from Playwright, Vitest, Storybook etc.; Chromatic has the deepest Storybook integration but is hosted; **[conflict]** Argos pricing figures differ between sources — [Argos: best VRT tools 2026 (vendor)](https://argos-ci.com/blog/best-visual-regression-testing-tools), [toolradar comparison](https://toolradar.com/compare/argos-vs-chromatic)
- Storybook MCP (`npx storybook add @storybook/addon-mcp`) lets agents read component docs, generate stories and run tests; its docs toolset depends on a components manifest (off by default) so "agents will be equipped to reuse your existing components and follow your documented usage guidelines"; Storybook 10.4 docs describe AI features as preview and React-only; Storybook 11 is in alpha — [Storybook MCP overview](https://storybook.js.org/docs/ai/mcp/overview), [Storybook 10.4 AI](https://storybook.js.org/docs/10.4/ai), [Storybook 11 alpha MCP docs](https://storybook.js.org/docs/11/ai/mcp/overview)

- Atlassian's `ensure-design-token-usage` "Enforces usage of design tokens rather than hard-coded values" — [Atlassian ESLint](https://atlassian.design/components/eslint-plugin-design-system/ensure-design-token-usage)

### Inferences
- **Mockups as source of truth, made machine-checkable.** Store mockup HTML + shared CSS read-only in the repo (e.g. `docs/design/night-rehearsal/`) with a hash file; workers may read but never edit them. Derive three artefacts once, in a dedicated step, and review them with the owner: (a) reference PNGs of each mockup rendered by Playwright in the same Docker image, fonts and viewports as the app; (b) a token inventory parsed from the shared CSS (custom properties → Night Rehearsal roles); (c) a component inventory mapping each mockup class to an `app/ui` component/variant, plus `aria.yml` structure templates per screen (mockups likely lack proper ARIA, so the template is written to the *intended* semantics, not the mockup's).
- **Three-layer fidelity check per screen/component** (measurement over eyeballing):
  1. *Structure:* `toMatchAriaSnapshot` against the reviewed `aria.yml` (landmarks, headings, controls and their names) — catches missing/extra regions and wrong semantics without pixel noise.
  2. *Style probes:* a Playwright helper reads `getComputedStyle` and `getBoundingClientRect` for named anchors (by role/name or `data-testid`) in both the mockup render and the app render and compares font family/size/weight/line-height, colour (normalised to OKLCH, ΔE tolerance), padding, gap, radius and box size within ±1–2 px. These numbers are what the agent iterates on.
  3. *Pixels:* mockup-vs-app screenshot diff with masks for data-driven regions (waveform canvas, song titles, timers) and a generous threshold, used as a smoke signal plus a diff heatmap for the human reviewer — not as the acceptance gate, because mockup content and app content differ.
  After owner sign-off, the app screenshot becomes the regular `toHaveScreenshot` baseline (doc 28 matrix), and the mockup comparison is retired for that screen.
- **Token-membership check.** A cheap custom e2e assertion: walk the rendered DOM, collect computed `color`, `background-color`, `border-color`, `outline-color`, `fill`, `stroke`, and assert every value is one of the resolved token values for the active appearance. This catches inline styles, arbitrary values and SVG fills that static lint misses.
- **Stopping one-offs mechanically.** Extend `check-ui-tokens.mjs` (or add Biome/ESLint rules) to: ban Tailwind arbitrary values for colour, spacing, radius, font-size and shadow (`[…]` with px/rem/colour) outside `packages/ui-tokens`; ban `style={{…}}` colour/size literals; restrict `@base-ui/react` imports to `apps/web/app/ui/**`; restrict feature code to importing visual primitives from `app/ui` only; require a `*.stories.tsx` for every exported `app/ui` component; ban the old role names once migrated. Expose the component inventory to agents (Storybook MCP components manifest if it supports this React/Vite setup, otherwise a generated `app/ui/INVENTORY.md`-style index from TS props).
- **Tool choice in personal mode.** Playwright `toHaveScreenshot` (already chosen in doc 28) or Vitest browser `toMatchScreenshot` for stories; skip Chromatic (hosted/paid) and Lost Pixel (shutting down); Argos only if a hosted review UI is ever wanted.

## 4. Accessibility gates during a redesign: axe in stories and e2e, keyboard-only flows, focus visibility, target size, reduced motion, colour-not-alone; what automated checks catch vs miss

### Takeaway
axe in stories and e2e is necessary but covers only part of WCAG (Deque/Storybook: "up to 57%" of issues), and Storybook's default axe ruleset is WCAG 2.0/2.1 A/AA plus best practices — WCAG 2.2 rules must be opted into. A dark redesign mainly risks focus visibility, non-text contrast, focus being obscured by sticky chrome, and target size, which need explicit token tests and scripted keyboard/geometry checks on top of axe.

### Cited Findings
- Storybook 10.6 a11y: `parameters.a11y.test` = `'off' | 'todo' | 'error'`; in CI, tests with `'error'` run automatically with the Vitest addon; `context` include/exclude, `config` passed to `axe.configure()`, `options.runOnly`; by default the rulesets are "WCAG 2.0 and 2.1 Level A and AA rules plus best practices"; the `region` rule is disabled by default; axe-core "automatically catches up to 57% of WCAG issues"; browser-based tests catch more than linters because they evaluate the rendered DOM — [Storybook: Accessibility tests](https://storybook.js.org/docs/writing-tests/accessibility-testing)
- **[outdated, partly]** The Storybook test-runner is superseded by the Vitest addon but still documented as an option "if you cannot use the Vitest addon" — [Storybook: Accessibility tests](https://storybook.js.org/docs/writing-tests/accessibility-testing); some third-party pages call it deprecated since Storybook 9 — [skills.cat storybook-testing](https://skills.cat/skills/yonatangross/orchestkit/storybook-testing) (secondary)
- WCAG 2.2 2.5.8 Target Size (Minimum), AA: pointer targets at least 24×24 CSS px, with exceptions for spacing (24 px offset to adjacent targets), inline targets and essential sizes; Deque recommends the AAA 44×44 where possible — [Deque: WCAG 2.2 updates](https://dequeuniversity.com/resources/wcag-2.2)
- WCAG 2.2 2.4.11 Focus Not Obscured (Minimum), AA: the focused item must not be entirely hidden by author-created content (2.4.12, AAA, requires it fully visible); **[conflict]** several secondary sources misstate its level — [Deque: WCAG 2.2 updates](https://dequeuniversity.com/resources/wcag-2.2), [W3C: What's new in WCAG 2.2](https://w3.org/WAI/standards-guidelines/wcag/new-in-22/) (page returned 403 to the fetcher; level confirmed via search results)
- Linear stress-tested both light and dark for contrast and elevation, and its contrast input enables very high-contrast themes — [Linear part II](https://linear.app/now/how-we-redesigned-the-linear-ui)
- Repo: `check-ui-tokens.mjs` already blocks removing outlines without a `focus-visible` replacement and ad-hoc motion classes; doc 28 sets `test: 'error'` globally and requires a WCAG-criterion comment for any per-story rule downgrade — [scripts/check-ui-tokens.mjs](scripts/check-ui-tokens.mjs), [docs/specs/28-ui-quality-and-design-review.md](docs/specs/28-ui-quality-and-design-review.md)

### Inferences
- **Opt into WCAG 2.2 rules.** Set axe `runOnly` tags to include `wcag22aa` (alongside `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `best-practice`) in Storybook and in the e2e axe helper, otherwise target-size checks don't run (verify the tag and the `target-size` rule name against the installed axe-core version).
- **What axe catches here:** text contrast on solid backgrounds, missing names/labels, invalid ARIA, duplicate IDs, some target-size cases. **What it misses or gets wrong:** focus indicator visibility/contrast (1.4.11 for the ring, 2.4.7, 2.4.13), focus obscured by the sticky transport bar/pedal HUD (2.4.11), focus order and traps, keyboard operability of custom widgets (waveform scrubber, mixer faders, loop handles), contrast over gradients/translucency/canvas, colour-only meaning (confidence colours, stem colours), motion and reduced-motion behaviour, and the quality of accessible names.
- **Extra gates to add for the redesign:**
  - Token tests: focus ring vs every surface and vs filled accent controls ≥ 3:1; non-text UI (borders of inputs, slider tracks, fader thumbs) ≥ 3:1 against adjacent colours; every state in every appearance × contrast context.
  - Story `play` tests for every interactive state with keyboard only; a `Focus` story per component screenshot-tested so the ring is visible in each theme.
  - e2e keyboard journeys (import → analyse → practice loop → mixer) driven only by `keyboard.press`, asserting the focused element after each step; a helper that, for each Tab stop, checks the focused element's rect isn't fully covered (`document.elementFromPoint` at several points) — 2.4.11.

  - Reduced motion: run a subset of e2e and stories with reduced-motion emulation (Playwright `emulateMedia({ reducedMotion: 'reduce' })`) and assert no non-essential animation (computed `animation-name`/`transition-duration`), keeping the playhead functional.
  - Colour-not-alone: story review rule + a test that confidence/stem indications carry a text/shape/pattern channel (e.g. `aria-label`/icon present), consistent with CLAUDE.md's "Confidence never shown by colour alone".

## 5. Performance gates for a real-time practice UI (playhead, waveform): INP, long tasks, rAF budgets, layout thrash; testing in CI

### Takeaway
Use Chromium-only lab gates in CI: drive the practice screen with Playwright under CPU throttling, collect Long Animation Frames (>50 ms) and INP-style interaction latency over repeated runs, and assert budgets (p75), plus a static rule that the playhead animates via compositor-only properties and never reads layout after writes. The redesign itself introduces the main new perf risks (blur/backdrop-filter, large shadows, gradients, font swaps), so the gates must exist before restyling the practice screen.

### Cited Findings
- Long Animation Frames API shipped in Chrome 123 (origin trial 116–122); a long frame is one where the rendering update is delayed beyond 50 ms; INP guidance is to respond in 200 ms or less; prefer `PerformanceObserver` over `getEntriesByType` because the buffer can drop entries; entries attribute contributing scripts — [Chrome: Long Animation Frames API](https://developer.chrome.com/articles/long-animation-frames)
- "main-thread congestion is one of the main causes for long INP, but INP itself doesn't help diagnose the root cause" (motivation for LoAF) — [w3c/long-animation-frame](https://github.com/w3c/long-animation-frame)
- LoAF is not Baseline across browsers, so keep a guarded observer; in CI, run the interaction N times and assert P75 against the budget; throttle CPU 4–6× because desktop runs hide regressions — [Tessl: web-vitals-inp-deep](https://tessl.io/registry/testland/web-vitals-inp-deep) (third-party skill, not authoritative)
- Forced synchronous layout ("forced reflow") happens when JS reads a layout value after a style change; layout thrashing is doing it repeatedly (e.g. reading `offsetWidth` then writing widths in a loop); "always batch your style reads and do them first"; ~16 ms per frame during animation; `requestAnimationFrame` schedules work at the start of a frame; DevTools has a Forced Reflow insight and LoAF exposes `forcedStyleAndLayoutDuration` in the field — [web.dev: Avoid large, complex layouts and layout thrashing](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing)
- Taboola used LoAF during the origin trial to measure field impact on INP — [web.dev: Taboola INP case study](https://web.dev/case-studies/taboola-inp)

### Inferences
- **CI perf spec (Chromium project only, since WebKit has no LoAF):**
  1. Open a fixture analysis on the practice screen, start playback with a loop, let it run a fixed duration (e.g. 20 s) with CPU throttled (CDP `Emulation.setCPUThrottlingRate`, 4×) while a `PerformanceObserver({type:'long-animation-frame', buffered:true})` collects entries.
  2. Assert: zero LoAF entries attributed to playhead/waveform code; total LoAF count below a small budget; no entry with `forcedStyleAndLayoutDuration > 0` from app scripts during steady-state playback.
  3. Measure interaction latency for the practice actions (play/pause, loop nudge, tempo change, mixer fader keyboard step) via Event Timing (`web-vitals` `onINP` or `PerformanceObserver({type:'event'})`), N≥10 repetitions, assert p75 ≤ 100 ms in lab (well under the 200 ms "good" field threshold, leaving headroom for slower devices).
  4. Record baselines in stage 0 and fail on regression beyond a margin, so the redesign is compared to the old UI, not to an absolute number alone.
- **Redesign-specific rules:** playhead/cursor moves via `transform` only (no `left`/`width`, no layout reads in the rAF callback); waveform drawn once to canvas/offscreen and only the overlay moves; no `backdrop-filter`/large blur behind the moving playhead or over the waveform; avoid animating `box-shadow`, gradients or `filter`; prefer static elevation tokens over shadows in the practice view; ensure font swap can't reflow the transport bar during playback (metric-matched fallback, §6); reduced-motion must not stop the playhead itself (it's information, not decoration).
- Keep perf tests out of the screenshot job to avoid noisy timing; run them on the same pinned Docker image with a fixed viewport.

### Gaps
- No authoritative published Playwright example asserting on `long-animation-frame` entries or rAF frame budgets was found; the CI recipe above is inferred from Chrome/web.dev docs and a third-party guide.
- Did not verify whether Splitune's waveform currently uses canvas, SVG or DOM; budgets should be set after measuring stage-0 baselines.

## 6. Font and asset handling: self-hosting variable fonts with subsetting (keeping `tnum` and features), FOUT/CLS control, licensing (OFL)

### Takeaway
Both new families are OFL 1.1 variable fonts that can be self-hosted and subset; the critical detail is that `pyftsubset`'s default feature list drops `tnum` (and stylistic sets), so subsetting must keep `--layout-features='*'` (as Splitune's script already does) and a test should prove `tnum` survives. Control CLS with metric-matched fallbacks (`size-adjust` and friends), preload only the one critical file, and choose `font-display` per role.

### Cited Findings
- `pyftsubset --layout-features` defaults keep only `calt, ccmp, clig, curs, kern, liga, locl, mark, mkmk, rclt, rlig` plus script-shaping features, so `tnum` is dropped unless added (`--layout-features+=tnum`) or all are kept with `'*'`; WOFF2 output needs Brotli (`--flavor=woff2`); characters are selected with `--unicodes` (a common pattern reuses Google Fonts' Latin `unicode-range` list) — [clagnut: How to subset a variable font](https://clagnut.com/blog/2418), [fontTools subset source](https://fuchsia.googlesource.com/third_party/fonttools/+/69a532cfbb5294a0c96cc3f9d092db7bad2339f9/Lib/fontTools/subset/__init__.py), [Vikunja subset script](https://kolaente.dev/k2s/frontend/src/branch/main/scripts/fonts-subset.sh)
- Repo: `subset.sh` keeps every layout feature and variation axes, limits Inter `wght` to 400–700 with `varLib.instancer` to stay under an 80 KB preloaded budget, and notes that Fontsource subsets strip `tnum/cv*/ss*` — [scripts/fonts/subset.sh](scripts/fonts/subset.sh); only the Inter roman file is preloaded and a metric-matched "Inter Fallback" is defined — [packages/ui-tokens/src/fonts.css](packages/ui-tokens/src/fonts.css)
- Instrument Sans: SIL OFL 1.1; axes `wdth` 75–100 and `wght` 400–700 per the project README; README lists `tnum` among its OpenType features — [Instrument/instrument-sans](https://github.com/Instrument/instrument-sans), [Fontsource Instrument Sans](https://cdn.jsdelivr.net/npm/@fontsource-variable/instrument-sans@5.3.0/README.md); **[conflict]** a third-party catalogue lists `wght` 100–900 — [fontalternatives](https://fontalternatives.com/fonts/instrument-sans/)
- JetBrains Mono: licence changed from Apache 2.0 to SIL OFL 1.1 in v2.002; variable format added in v2.001; Fontsource lists weights 100–800 — [JetBrains/JetBrainsMono releases](https://github.com/JetBrains/JetBrainsMono/releases), [npm: @fontsource-variable/jetbrains-mono](https://npmjs.com/package/@fontsource-variable/jetbrains-mono); **[outdated]** some listings still say "OFL 1.1 and Apache 2.0" — [LinuxLinks](https://www.linuxlinks.com/jetbrains-mono-monospaced-typeface-developers/)
- web.dev: self-hosting isn't automatically faster (needs CDN + HTTP/2); preload only the most important fonts, and "preload ignores `unicode-range`"; inline `@font-face` and critical CSS in `<head>`; `font-display: optional` (100 ms block, no swap) is best for performance/avoids swap shifts, `swap` "delays text render the least" but can shift, `fallback` limits the swap window to 3 s; combine strategies; use `size-adjust` on the fallback to reduce CLS; WOFF2 "compresses 30% better than WOFF"; variable fonts don't always win if only one style is used; check licences before subsetting/self-hosting — [web.dev: Best practices for fonts](https://web.dev/articles/font-best-practices)

### Inferences
- **Concrete font plan:** extend `subset.sh` with pinned, SHA-checked upstream files for Instrument Sans (roman + italic if used) and JetBrains Mono (roman only unless code italics are used), keep `--layout-features='*'`, instance `wght` to the weights the Night Rehearsal type scale actually uses (and `wdth` to the used range or a fixed value) to stay under the existing 80 KB preload budget; preload only Instrument Sans roman; load JetBrains Mono on first use (`font-display: swap` or `optional` depending on whether mono appears above the fold, e.g. BPM/time readouts in the transport).
- **`tnum` proof:** add a test (fontTools `ttx -t GSUB` or a Python/JS font parser) asserting the shipped WOFF2 files contain `tnum` (and any `ss*`/`cv*` the mockups use); add a story/e2e check that time/BPM/fret readouts use `font-variant-numeric: tabular-nums` and don't change width as digits tick (measure the box width across values) — matters for a moving transport readout.
- **CLS:** generate metric-matched fallbacks (`size-adjust`, `ascent-override`, `descent-override`, `line-gap-override`) for Instrument Sans vs Arial/system and JetBrains Mono vs a system mono; verify with a Playwright CLS measurement on first load (fonts blocked vs allowed) — `ascent-override` etc. are inferred from standard practice; web.dev's page only names `size-adjust`.
- **PWA:** add new font files to the service-worker precache with content hashes and remove the Inter files at cleanup so offline users don't keep stale fonts; update licence files beside the fonts.
- **Licensing:** OFL permits self-hosting, embedding and subsetting; ship `OFL.txt` beside each font (as the script already does for Inter/Atkinson).

### Gaps

- The exact Instrument Sans axis ranges in the current upstream release (400–700 vs 100–900) need confirming from the file itself.
