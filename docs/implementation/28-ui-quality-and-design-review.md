# UI quality workflow and design review

How Splitune keeps the UI consistent, accessible and good-looking as steps 10–20 add screens: Storybook as the component workbench, automated checks (tokens, a11y, visual regression), the design QA checklist every UI change passes, and the small usability rounds personal mode can afford. Tokens and components: `26-design-system.md`; screens and copy: `27-screens-flows-and-content.md`; the wider test pyramid: `18-testing-strategy.md`.

> **Personal mode (`25-personal-mode.md`):** everything here is free and local — no Chromatic, no hosted review UI, no device cloud. Usability rounds are the owner plus 3–5 friends.

## TL;DR
- **Storybook 10.6** in `apps/web` is the workbench: every `app/ui` and `packages/notation` component has one story per state, rendered under a theme × contrast × density toolbar; `@storybook/addon-a11y` runs axe with `test: 'error'` and `@storybook/addon-vitest` runs stories as tests in CI.
- **Token tests** in `packages/ui-tokens` fail the build if any semantic pair drops below its WCAG minimum, leaves sRGB gamut, or if two stem colours become indistinguishable under simulated colour-vision deficiency.
- **Visual regression** with Playwright `toHaveScreenshot` against a fixed matrix (key screens × Light/Dark/Stage × 3 viewports), run inside the pinned Playwright Docker image so baselines are stable; baselines are committed as test fixtures.
- **Lint guards:** no raw colour literals outside `ui-tokens`; no `outline: none` without a replacement; no Tailwind palette classes (palette is cleared).
- **Design QA checklist** (§5) is part of the definition of done for any story that changes UI, and the whole checklist is run once on every screen in step 15a before the MVP gate.
- **Usability rounds** (§6): three tasks with time targets, run on the owner's devices at a real music stand, before G1 and after any major UX change.

## 1. Where UI code lives
| Path | Contents |
|---|---|
| `packages/ui-tokens` | Primitives, themes, Tailwind mapping, fonts CSS, typed token metadata, token tests |
| `apps/web/app/ui/` | shadcn/Base UI components (generated by the CLI, then owned), Splitune kit, icons |
| `apps/web/app/features/*/` | Feature components composed from `app/ui`; no new visual primitives here |
| `packages/notation` | `AlphaTabView` + overlay (confidence, loop shading, current bar) |
| `apps/web/.storybook/` | Storybook config, decorators, test setup |
| `apps/web/e2e/visual/` | Visual regression specs; baselines in `__screenshots__/` |

Rule: a feature that needs a new visual pattern adds it to `app/ui` with stories first, then uses it.

## 2. Storybook
- **Version and addons:** `storybook` 10.6.x with `@storybook/react-vite`, `@storybook/addon-a11y`, `@storybook/addon-vitest` (Vitest 5 browser mode, Playwright provider). Versions re-verified when installing (`00-tech-stack.md`).
- **Global toolbar/decorators:** Appearance (Light / Dark / Stage), Contrast (normal / more), Density (browse / practice), Distance (Desk / Stand / Floor), Reduced motion, Direction placeholder (LTR only for now). Decorators set the same `data-*` attributes as the app (`26` §2), so stories prove the real theming path.
- **Story conventions:** `Component.stories.tsx` beside the component; one story per state from `26` §12.3 (`Default`, `Hover`, `Focus`, `Pressed`, `Disabled`, `Loading`, `Error`, plus domain states like `ConfidenceLow`, `RoughStem`, `LoopResting`); interaction tests with `play` functions for keyboard paths; realistic content (real song titles from fixtures, long titles, two-digit frets).
- **Fixtures:** stories use `packages/contracts/fixtures` (the 8-bar Am–F–C–G example) so notation, chord strip and mixer stories render real artefacts with low-confidence notes.
- **a11y:** `parameters.a11y.test = 'error'` globally; a story may downgrade a specific rule only with a comment naming the WCAG criterion and why (e.g., canvas waveform `aria-hidden` with a text alternative elsewhere).
- **Commands:** `pnpm --filter web storybook` (dev), `pnpm --filter web storybook:build`, `pnpm --filter web test:stories` (Vitest project running every story in Chromium + WebKit, a11y included). CI runs `test:stories`.

## 3. Automated design checks
| Check | Where | Fails when |
|---|---|---|
| Contrast table | `packages/ui-tokens/src/contrast.test.ts` (colorjs.io, gamut-mapped to sRGB) | Any pair in `26` §4.6 (and every `*-foreground`/surface pair) drops below its minimum in any appearance × contrast context |
| Gamut | same | A semantic token resolves outside sRGB (clipping would change the tested ratio) |
| CVD separation | `palette.test.ts` | Any two `--stem-*` colours have ΔE2000 < 12 under simulated protanopia, deuteranopia or tritanopia (Machado 2009 matrices), per appearance |
| Token naming | `tokens.test.ts` | A semantic role is missing in one appearance, or a component token references a primitive directly |
| Raw colours | `scripts/check-ui-tokens.mjs` (in `pnpm lint`) | `#hex`, `rgb(`, `hsl(`, `oklch(` literals in `apps/**` or `packages/**` outside `ui-tokens` (SVG icon `currentColor` is fine) |
| Motion | same script | Numeric/arbitrary `duration-*` or `delay-*` (except `duration-0`), stock or arbitrary `ease-*`, or millisecond literals in an arbitrary `[transition:…]` (step 15a) |
| Focus | same script | `outline: none`/`outline-none` without `focus-visible:outline-*` in the same rule or class list |
| Copy keys | `apps/web` unit test | A user-facing string in a component is not a Paraglide message, or a catalogue key from `27` §5.6 is missing or its copy differs from the catalogue (step 15a) |
| a11y | Storybook (all stories) + Playwright pages | axe serious/critical violations |
| Bundle | `bundle-size` job (`02` §5) | Practice route JS >300 KB gzip (fonts and alphaTab excluded) |

## 4. Visual regression
- **Tool:** Playwright 1.64 `expect(page).toHaveScreenshot()` (pixelmatch, `maxDiffPixels: 20` with the default per-pixel threshold — step 15a, see notes — animations disabled, caret hidden, `stylePath` hiding volatile UI such as timestamps and the now-line).
- **Stable rendering:** run in `mcr.microsoft.com/playwright:v1.64.x-noble` (exact tag pinned in `package.json` script) locally and in CI; fonts are self-hosted so the image needs none installed. `pnpm --filter web e2e:visual` and `e2e:visual:update`.
- **Matrix (keep it small; ~36 images):**

| Screen (with fixture data) | Appearances | Viewports |
|---|---|---|
| Home, Library (populated), Import (file selected) | Light, Dark | Phone 390×844, tablet 1180×820, desktop 1440×900 |
| Practice (tab ready, loop active, low-confidence notes visible) | Light, Dark, Stage | same |
| Practice progressive state "stems ready, tab pending" | Light | tablet |
| Mock checkout, Settings → Display | Light | phone, desktop |

- **Baselines** live in `apps/web/e2e/visual/__screenshots__/` and are committed: they are test expectations (like the committed contract schemas), not build output. Update only with an intentional UI change, in the same commit, and look at every diff image before accepting it.
- Engines: Chromium and WebKit (Firefox renders fonts differently enough to double the baselines for little gain; it is covered by functional E2E).

## 5. Design QA checklist (definition of done for UI changes)
Run on the changed screens (and every screen in step 15a). Record pass/fail in the PR description or `PROGRESS.md`.

**Visual quality**
- [ ] Uses only tokens and `app/ui` components; no one-off colours, radii, shadows or font sizes.
- [ ] Clear hierarchy: one primary action per region; headings, body and secondary text use the scale in `26` §6.2.
- [ ] Alignment on the 4 px grid; consistent gutters (16/24/32); no orphaned elements or uneven gaps.
- [ ] Long content handled: 80-character song titles, 2-digit frets, 20-minute songs, empty lists, 1-item lists.
- [ ] Looks right in Light, Dark and Stage (and the score stays paper in Dark).

**Practice at a distance**
- [ ] At the stand (tablet at 0.75 m), fret digits and the current chord are readable without leaning in; at 1.5 m the phone glance view is readable.
- [ ] Primary practice controls hit reliably with a knuckle while holding a pick (10 tries, ≥9 hits).
- [ ] Every action has a key; pedal (or arrow keys) works without the page scrolling; `PedalHud` confirms each action.

**Accessibility**
- [ ] Keyboard-only pass in visual order; focus always visible and never hidden by sticky bars.
- [ ] 200% text zoom and 320 px reflow (WCAG 1.4.4, 1.4.10) on browse screens; no clipped text.
- [ ] Colour never the only cue (confidence, stems, status, selection); check with a CVD simulator.
- [ ] `prefers-reduced-motion` and "Increase contrast" behave per `26` §2, §10; Windows forced colours spot check in Chromium emulation.
- [ ] Screen-reader names for icon buttons; live announcements for stage changes and pedal actions; notation text alternative present (`12` §9).

**States and copy**
- [ ] Empty, loading, partial, error and offline states from `27` §4 implemented and storied.
- [ ] Copy comes from the catalogue (`27` §5.6) and follows the style rules (sentence case, verbs, numerals, units, 1-based bars).
- [ ] Locks and limits follow `23` §5 (only at point of action, exact numbers and dates).

**Performance feel**
- [ ] No layout shift when artefacts arrive; skeletons match final layout.
- [ ] Interactions respond within 100 ms (pressed state at least); no long tasks >50 ms during playback.

## 6. Usability rounds (personal mode)
Participants: the owner + 3–5 friends who play guitar or bass (include at least one beginner and, if possible, one player over 45). Setup: their own instrument, the owner's iPad on a music stand and a phone; bright room and dim room. Think-aloud, no help unless stuck for 60 s.

| Task | Success | Target |
|---|---|---|
| From a fresh browser, reach a slowed loop of the example song's guitar part | Loop playing at ≤80 % | ≤5 min, no help (G1 input, `20` E8) |
| Import a song from a file, loop bars 9–12 at 70 % with count-in, mark one clean pass using only the keyboard/pedal | All steps done | ≤4 min after the song is playable |
| Find and fix a chord marked unsure | Edit saved and visible after reload | ≤2 taps to an alternative; participant can say what the "?" means |

Also ask: "From where you're sitting, read me bar 6." (legibility) and "What does Splitune think it got wrong?" (confidence comprehension). Log findings with severity in `PROGRESS.md`; fix severity-1 issues before the next step.

## 7. Review rubric for "beautiful and professional"
Use when comparing alternatives or reviewing a screen; each item 1–3, a screen ships at ≥2 on every item.
| Item | 3 looks like |
|---|---|
| Focus | The music (or the one task of the screen) is unmistakably the main thing |
| Restraint | Colour only where it means something; one accent; no decorative gradients or shadows |
| Rhythm | Spacing follows the scale; edges line up across regions |
| Typography | Few sizes, clear weights, tabular numbers; nothing below 12 px |
| Consistency | Same component, same behaviour, same words everywhere |
| Honesty | Uncertainty, limits and failures are visible and explained |
| Calm | Nothing blinks, nags or celebrates without being asked |

## Implementation notes (step 10, 2026-10-22)
- Screens have stories under **Screens/** (Library, Import, Practice progress, Auth, Settings, System, Home) rendered with a memory router and a fixture-seeded Query cache (`apps/web/.storybook/app.tsx`, `app/features/story-fixtures.ts`); unseeded queries fail against Storybook's own server, which is how error states are shown. Storybook uses `vite.base.ts` (no Start/Nitro plugins).
- Page-level checks: Playwright + `@axe-core/playwright` (WCAG 2.2 AA tags, no serious/critical) on landing, library and import, plus a no-horizontal-scroll check; E2E contexts emulate reduced motion so axe never samples a colour transition mid-way.

## Implementation notes (step 15a, 2026-10-22)
- **Visual suite as built** (`apps/web/e2e/visual/`, `playwright.visual.config.ts`, `scripts/visual.mjs`): screens are the **Screens/ stories of the built Storybook** (fixture data, no backend, deterministic), not the running app — the stories render the real shells and feature components, and the Docker run needs no database, workers or audio. The clock is fixed (`2026-10-22T10:00Z`, UTC, `en-GB`) so relative dates, renewal dates and the evening Stage hint never change. Matrix: the §4 table plus step 15's screens (Settings → Privacy phone/desktop, account deleted phone, practice stems expired tablet) = **36 images × Chromium + WebKit**; "Practice" is `Screens/Practice/LoopActive` (tab ready, `?loop=5-6`, the fixture's unsure notes), "stems ready, tab pending" is `Screens/Practice/Chords`. A focus spec in the same harness checks that a focused control scrolls clear of the sticky app bar (WCAG 2.4.11).
- **Docker:** `scripts/visual.mjs` builds Storybook, starts `npx playwright@<same version> run-server` inside `mcr.microsoft.com/playwright:v1.64.1-noble` (tag pinned in `package.json`) **as `linux/amd64`** and runs the tests on the host with `connectOptions.exposeNetwork: '<loopback>'`. Measured: arm64 and amd64 containers differ in 36 of 72 images at zero tolerance (24 WebKit, 12 Chromium), so baselines are amd64 everywhere (Rosetta on Apple Silicon: ~3 min for 74 tests). The config refuses to run without the container endpoint.
- **Tolerance:** `maxDiffPixelRatio: 0.002` let a `--radius` 10 → 16 px change pass on 69 of 72 images (it is ~2,600 px at 1440×900; the corner changes were ~450 px). Zero tolerance failed once in two runs on a 3×2 px waveform-canvas wobble. `maxDiffPixels: 20` (default per-pixel threshold): green on repeated runs, and the radius change failed **all 72** images.
- **Storybook wrapper:** `Screens/*` stories render edge to edge (the decorator's 24 px margin is for components only) — this was the "31 px overflow at 320 px" noted in steps 14–15.

## Implementation notes (step 16, 2026-10-23)
- **Forced colours:** axe under Chromium's forced-colours emulation found CanvasText on Highlight (1.85:1) wherever a selected or pressed surface used `bg-accent` behind ordinary text (radio/choice cards, field labels, toggles, transport buttons, drop zone, current nav item). Those use `forced-colors:…:bg-card` (or pair `forced-colors:text-accent-foreground` on the nav); the Highlight border still marks the state.
- **Reflow:** a real phone resolves distance to Floor, which made Home's product stills 171 px wider than the screen (the 15a sweep rendered stories at the Desk default); the stills are pinned to Desk and crop at 320 px. The signed-in app bar overflowed by 19 px at 320 px; it is tighter below `sm` (phone baselines updated). Checked by `a11y.spec.ts` on every project.
- **200 % text:** library and practice keep their content and controls (no horizontal scroll; Play, speed and loop badge reachable) in every desktop engine; screenshots are attached to the test results.
- **Performance:** no Long Animation Frame ≥ 50 ms during steady playback (desktop Chromium, 12 s with count-in and loop wraps). The first Play press is one ~111 ms frame: `new AudioContext()` in `createEngine` (the browser opening the audio device), which iOS requires inside the gesture — recorded, not changed. Capo → tab redrawn with the CPU slowed 4× on a Galaxy Tab viewport: median 36 ms (8-bar example; budget 300 ms); `buildTab` on a dense 4-minute part in Node: 7.6 ms (simplified) / 17.7 ms (as played) mean.
